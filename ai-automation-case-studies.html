Why I built these back to back

I didn't want a single polished demo — I wanted to prove the same architecture holds up across genuinely different problems. Each project started from the same question: what decision here is actually a fact (something a rule can check), and what's a real judgment call that still needs a person? Getting that split right, and being honest in the code and the docs about what's live versus what's a documented next step, mattered more to me than any individual feature.

  1. LoadAudit AI came first, out of research into where freight brokerages are actually spending money on manual work right now — invoice reconciliation was the clearest, most cited pain point.
  2. Carrier Vet AI followed naturally — same brokerage, a different back-office decision, and a chance to test whether the pattern (rules engine + human-in-the-loop) would hold somewhere the stakes and inputs were completely different.
  3. Claims Intake AI pushed the pattern into a new industry on purpose. Insurance triage has a failure mode — a missed fatality claim — that can't be tolerated at all, so this is where I built a metric that reports that specific failure mode on its own line instead of letting it hide inside an aggregate accuracy score.
  4. Support Triage AI is the most broadly relatable of the four, and it's also where my own eval harness caught a real bug — a routine question was getting misrouted because of an overly broad keyword match. I fixed it and left the story in the docs instead of quietly deleting the evidence.

The pattern, if you only read one thing

Rules make the decision; the model gathers information

In all four projects, an LLM or a lookup step turns messy input into structured data — but the actual approve/flag/escalate decision comes from an explicit rules engine. That's what makes each system auditable: I can point to the exact line of logic behind any outcome.

Humans get interrupted only when there's a real decision left

Hard rejects, clean approvals, and routine auto-replies never page anyone. Slack alerts are reserved for the cases that actually need a judgment call — which is also what keeps the alerts worth paying attention to instead of becoming noise.

Every project is evaluated on labeled data, and the docs say what's real

Each README states plainly what's a working, tested code path and what's a documented next step — including the two ordering bugs my own eval harnesses caught and I fixed, rather than presenting a first-try demo as flawless.
